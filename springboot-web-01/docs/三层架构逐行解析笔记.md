# Spring Boot 三层架构逐行解析笔记

> 项目：springboot-web-01
> 范围：数据访问层 `UserDaoImpl` 与业务层 `UserServiceImpl`
> 主线：**分层解耦 = 面向接口编程 + IoC 容器管理对象 + 各层职责单一**

---

## 〇、三层架构全景

```
Controller（接收请求） → Service（处理业务） → DAO（取数据） → user.txt
```

| 层 | 包位置 | 注解 | 职责 |
|---|---|---|---|
| 表现层 | `com.itheima.controller` | `@Controller` / `@RestController` | 接收请求、返回响应 |
| 业务层 | `com.itheima.service` | `@Service` | 加工数据、业务规则 |
| 数据层 | `com.itheima.dao` | `@Repository` | 只管存取，不管加工 |

约定俗成：接口放上层包，实现类放下层 `impl` 子包（`UserDao` → `dao.impl.UserDaoImpl`）。

---

## 一、数据访问层：`dao/impl/UserDaoImpl.java`

> 数据层的接口实现 + `@Repository` 注入容器 + 只负责读文件返回原始数据。

### 逐行解析

```java
@Repository  //数据层Bean，交给Spring管理
public class UserDaoImpl implements UserDao {

    @Override
    public List<String> findAll() {
        InputStream in = this.getClass().getClassLoader().getResourceAsStream("user.txt");
        List<String> lines = IoUtil.readLines(in, StandardCharsets.UTF_8, new ArrayList<>());
        return lines;
    }
}
```

| 行 | 代码 | 讲解 |
|---|---|---|
| 12 | `@Repository` | Spring 启动时扫描到该注解，自动创建对象放进 IoC 容器（单例 Bean）。它是 `@Component` 的「语义版」：换成 `@Component` 也能跑，但看注解就知道 Bean 属于哪一层，语义清晰是分层的纪律 |
| 13 | `implements UserDao` | 实现 DAO 接口。类名 `UserDaoImpl` = 接口名 + Impl，Java 圈约定俗成。必须兑现接口声明的所有方法 |
| 15 | `@Override` | 声明这是重写方法。方法名拼错时编译器立刻报错，零成本的安全带 |
| 16 | `public List<String> findAll()` | 与接口签名一致。返回 `List<String>`：每行用户数据一个字符串（真实项目应为 `List<User>` 实体类，教程先简化） |
| 18 | `getResourceAsStream("user.txt")` | 拆开读：`this.getClass()` 拿当前类的 Class 对象 → `.getClassLoader()` 拿类加载器 → `.getResourceAsStream(...)` 去**类路径**找文件返回字节流。**类路径在哪**：文件放 `src/main/resources/user.txt`，Maven 编译后复制到 `target/classes/`（与 .class 同目录）——这就是类路径。不写死绝对路径，换机器照样跑 |
| 20 | `IoUtil.readLines(...)` | Hutool 工具三连：把流 `in` 按 UTF-8 编码逐行读完，塞进 `new ArrayList<>()`。没有 Hutool 就得自己 BufferedReader 循环读 + try-catch + finally 关流 |

### 本类要点

- **职责边界**：DAO 只管取数据、返回原始行，不管加工。过滤、拼业务逻辑是 Service 的事。
- **依赖引入**：Hutool 在 `pom.xml` 中引入。

## 二、业务层：`service/impl/UserServiceImpl.java`

> 调 DAO 拿生数据 → 解析成 User 对象 → 交给上层。既不懂 HTTP 也不懂文件 IO，只负责「把生数据变成业务上有意义的数据」。

### 逐行解析

```java
@Service //业务层
public class UserServiceImpl implements UserService {

    @Autowired //让 spring 把 userdao 的实现类对象注入进来(不用自己new)
    private UserDao userDao;

    @Override
    public List<User> findAll() {
        List<String> lines = userDao.findAll();

        List<User> userList = lines.stream().map(line -> {
            String[] parts = line.split(",");
            Integer id = Integer.parseInt(parts[0]);
            String username = parts[1];
            String password = parts[2];
            String name = parts[3];
            Integer age = Integer.parseInt(parts[4]);
            LocalDateTime updateTime =
                    LocalDateTime.parse(parts[5], DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss"));
            return new User(id, username, password, name, age, updateTime);
        }).toList();

        return userList;
    }
}
```

| 行 | 代码 | 讲解 |
|---|---|---|
| 13 | `@Service` | 与 `@Repository` 是亲兄弟：扫描后创建 Bean 放进 IoC 容器。三大注解功能无区别，只靠语义区分层 |
| 14 | `implements UserService` | 与 DAO 同套路：接口定标准（`service` 包），实现类干活（`service.impl`）。连业务层也拆接口，因为 Controller 将来也只面向 `UserService` 编程——每层对上层暴露「标准」，不是「实物」 |
| 16–17 | `@Autowired private UserDao userDao;` | ⭐ **全文件核心，解耦的兑现处**。变量声明的是**接口类型**，Spring 启动时把 `@Repository` 创建的 `UserDaoImpl` 对象注入进来。对象创建权从使用者手里变成 Spring 手里 = 控制反转（IoC）；Spring 递依赖的动作 = 依赖注入（DI）。初学疑问「没 new 不会空指针吗」——不会，注入发生在调用之前 |
| 20 | `List<User> findAll()` | 返回类型从 DAO 的 `List<String>` 变成 `List<User>`——两层职责边界的体现：DAO 给生数据，Service 加工成有意义的对象 |
| 22 | `userDao.findAll()` | 层与层之间的握手。Service 不碰文件、不碰 IO，只是打了个电话 |
| 25 | `lines.stream().map(line -> {...}).toList()` | Stream 流式处理：`.stream()` 建流水线 → `.map(...)` 对每个元素执行转换（进 String 出 User）→ `.toList()` 收集成 List（Java 16+ 写法，等价于 `.collect(Collectors.toList())`）。大白话：每行文本单独送进加工间，加工成 User 再装箱 |
| 26 | `line.split(",")` | 按逗号切开一行文本，下标从 0 起，顺序与文件字段严格对应 |
| 27 / 31 | `Integer.parseInt(...)` | 文件切出来全是字符串，id/age 需要转数字类型——解析工作中最常见的一步 |
| 32–33 | `LocalDateTime.parse(parts[5], ofPattern(...))` | 按样式 `yyyy-MM-dd HH:mm:ss` 把字符串翻译成日期时间对象 |
| 35 | `new User(...)` | 六参全参构造组装 User。能直接调是因为 User 类贴了 Lombok：`@Data`（自动 get/set）、`@NoArgsConstructor`（无参构造）、`@AllArgsConstructor`（全参构造）——实体类一行方法都没有，却什么都能干 |
| 38 | `return userList;` | 成品交给 Controller 层 |

### 已知小瑕疵（暂不改，知道即可）

第 32 行变量名叫 `updateTime`，但 `User` 类字段实际叫 `createTime`。构造器按位置传参所以能正常跑，纯命名不一致。真实项目这种「名不副实」要修，容易坑维护者。

## 三、解耦核心复盘

### 没解耦的写法（反面教材）

```java
private UserDao userDao = new UserDaoImpl();  // Service 与实现类焊死
```

数据源从 user.txt 换成 MySQL 时，要翻遍所有代码改 `new`——这就是「耦合」的代价。

### 解耦后的写法（本项目）

两个关键组合：

1. **面向接口**：`userDao` 声明为 `UserDao` 接口类型，Service 只知道「有个会 findAll 的东西」，不关心具体实现。
2. **IoC + DI**：`@Repository` 把实现类交给 Spring 创建；`@Autowired` 让 Spring 把 Bean 注入进来。

### 解耦的实际收益

明天数据源换 MySQL，只需新写：

```java
@Repository
public class UserDaoImplMysql implements UserDao { ... }
```

让 Spring 使用新 Bean（如原实现类改注解、或用 `@Primary`），**Service 一行都不用改**。

### 一句话总结

> 接口定标准、实现干脏活、Spring 牵线——三层架构的地基就是这么垒的。

数据流向：**user.txt → DAO 读成字符串行 → Service 解析成 User 对象 → Controller 返回给前端**。
