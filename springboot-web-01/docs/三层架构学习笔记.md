# 三层架构学习笔记

> 项目：`springboot-web-01`（Spring Boot 4.1.1 / Java 17 / Lombok / Hutool 5.8.27）
> 定位：把「分层解耦」从概念到代码到请求链路讲通的一篇总纲
> 配套文档：`IOC&DI.md`（注入方式细节）、`三层架构逐行解析笔记.md`（逐行代码）、`UserDaoImpl逐行笔记.md`

---

## 一、一句话结论

**三层架构不是为了代码好看，是为了「改一处不牵连其余」。**

它用两道保险实现这一点：

1. **面向接口编程**——上层只认接口，不认实现类；
2. **IoC / DI 容器管理对象**——对象不由使用者 `new`，由 Spring 创建并注入。

这两条合起来的效果：**换数据源、换实现、加业务规则，都只动一层，其余层零改动。**

---

## 二、分层是怎么来的（痛点 → 方案）

### 没分层时的样子

一个 Servlet 里干完所有事：

```
Servlet
 ├── 解析请求参数
 ├── 写业务规则（校验年龄、拼名称…）
 ├── 写 JDBC / 读文件
 └── 输出响应
```

问题很实在：

| 问题 | 具体表现 |
|---|---|
| 逻辑混杂 | 业务规则和数据库代码交织，改规则时容易误伤 SQL |
| 无法复用 | 同一套业务逻辑，Web 版和定时任务版要各写一遍 |
| 无法替换 | 换数据库＝翻遍所有 Servlet 改连接代码 |
| 无法测试 | 测业务规则必须起 Web 容器、连数据库 |

### 分层后的样子

按「职责」切开，每层只对上一层负责：

```
  浏览器 / 前端
       │  HTTP 请求
       ▼
┌─────────────────┐
│  表现层 Controller │  只做：收请求、调 Service、返回响应
└─────────────────┘
       │  调用接口（不懂 HTTP）
       ▼
┌─────────────────┐
│  业务层 Service    │  只做：业务规则、数据加工、事务
└─────────────────┘
       │  调用接口（不懂文件/数据库）
       ▼
┌─────────────────┐
│  数据层 DAO        │  只做：存取数据，返回原始数据
└─────────────────┘
       │
       ▼
   user.txt / MySQL / Redis
```

**核心判断标准**：某一层的代码里，出现另一层的技术细节（比如 Service 里写 `BufferedReader`、Controller 里写 SQL），就是越界了。

## 三、本项目文件地图

| 层 | 接口 | 实现类 | 注解 | 职责一句话 |
|---|---|---|---|---|
| 表现层 | 无需接口 | `controller/UserController.java` | `@RestController` | 暴露 `/list`，返回 JSON |
| 业务层 | `service/UserService.java` | `service/impl/UserServiceImpl.java` | `@Service` | 把文本行解析成 `User` 对象 |
| 数据层 | `dao/UserDao.java` | `dao/impl/UserDaoImpl.java` | `@Repository` | 从 classpath 读 `user.txt` |
| 实体 | — | `pojo/User.java` | `@Data` + Lombok | 承载数据，不属于任何一层 |

辅助文件：

| 文件 | 作用 |
|---|---|
| `resources/user.txt` | 8 行英雄数据，一行一个用户，逗号分隔 |
| `resources/static/user.html` | 前端页面，Vue + axios |
| `SpringbootWeb01Application.java` | 启动类，`@SpringBootApplication` 负责扫描 `com.itheima` 下的 Bean |

**包结构约定**（不是硬规定，但全行业都这么写）：

```
com.itheima
 ├── controller   表现层
 ├── service     业务层接口
 │    └── impl   业务层实现
 ├── dao         数据层接口
 │    └── impl   数据层实现
 └── pojo        实体类
```

> 口诀：**接口放外层包，实现放 `impl` 子包。** 一眼就能看出「这层对外承诺了什么」。

## 四、完整请求链路（把整个项目跑一遍）

这是本篇最该背下来的一张图——所有零散知识点都在这里归位：

```
①  浏览器访问 http://localhost:8080/user.html
         │
         │  Spring Boot 默认把 classpath:/static/ 当静态资源目录，
         │  所以 user.html、js/axios.min.js 能直接被访问（无需写任何代码）
         ▼
②  user.html 加载完 → Vue 的 mounted() 钩子执行 → 调用 search()
         │
         ▼
③  axios.get('/list')  发起异步请求
         │
         ▼
④  UserController.list()    ← @RequestMapping("/list") 完成路径映射
         │                     请求进入表现层
         ▼
⑤  userService.findAll()    ← @Resource(name="userService") 注入的 Bean
         │                     请求进入业务层
         ▼
⑥  userDao.findAll()        ← @Autowired 注入的 Bean
         │                     请求进入数据层
         ▼
⑦  UserDaoImpl 读 classpath 下的 user.txt
         │  返回 List<String>：["1,daqiao,1234567890,大乔,22,2024-07-15 15:05:45", ...]
         ▼
⑧  UserServiceImpl 用 Stream 把每一行解析成 User 对象
         │  返回 List<User>（此时数据才「有意义」）
         ▼
⑨  UserController 把 List<User> 返回
         │  @RestController = @Controller + @ResponseBody，
         │  Spring 自动用 Jackson 把对象转成 JSON 数组
         ▼
⑩  浏览器收到 JSON：[{"id":1,"username":"daqiao",...,"createTime":"2024-07-15T15:05:45"}]
         │
         ▼
⑪  Vue 用 v-for="user in userList" 循环渲染成表格
```

**留意第 ⑦⑧ 步的数据形态变化**，这就是分层的意义所在：

| 阶段 | 数据形态 | 说明 |
|---|---|---|
| DAO 返回 | `List<String>` | 生的文本行，纯粹是「存的东西」 |
| Service 返回 | `List<User>` | 加工后的对象，才是「能用的东西」 |
| Controller 返回 | JSON 字符串 | 网络传输格式，前端才认 |

**每一层都在把数据翻译成上一层能理解的形式。**

## 五、Bean 是怎么被组装起来的（启动期视角）

运行期的调用链是「Controller → Service → DAO」，但**创建顺序正好相反**——这点很多人一开始会绕晕：

```
Spring 启动
   │
   ├─ 扫描 com.itheima 包，发现四个注解
   │
   ├─ ① 创建 UserDaoImpl        （@Repository）
   │       什么都没依赖 → 直接造好，放进容器
   │
   ├─ ② 创建 UserServiceImpl    （@Service）
   │       发现 @Autowired UserDao → 去容器里找 → 拿到 UserDaoImpl 塞进去
   │
   ├─ ③ 创建 UserController     （@RestController）
   │       发现需要 UserService → 去容器里找 → 拿到 UserServiceImpl 塞进去
   │
   └─ 启动完成，三个 Bean 形成一个连好的整体

容器内部最终形态：
UserController
    └── userService → UserServiceImpl
                            └── userDao → UserDaoImpl
```

**关键理解**：依赖注入在你调用方法之前就完成了，所以 `userDao` 全程没有 `new` 也不会空指针。对象之间的「接线」是 Spring 干的活，你只负责声明「我需要什么」。

> 这就是「控制反转（IoC）」的字面含义：**对象的创建权和组装权，从你手里反转到了容器手里。**
> 详细解剖见 `IOC&DI.md`。

## 六、解耦的两个抓手（附反面教材）

### 抓手 1：面向接口

```java
// ❌ 耦合写法
private UserDao userDao = new UserDaoImpl();

// ✅ 解耦写法：只声明接口类型
@Autowired
private UserDao userDao;
```

区别不在「少写几个字」，而在于：

| | 耦合写法 | 解耦写法 |
|---|---|---|
| 依赖的对象 | 具体实现类 `UserDaoImpl` | 抽象接口 `UserDao` |
| 换实现时 | Service 得跟着改 | Service 一行不动 |
| 能否单测 | 必须真读文件 | 可塞入假实现（Mock） |
| 谁负责创建 | 使用者 | Spring 容器 |

### 抓手 2：IoC / DI

- `@Repository` / `@Service` / `@Controller` / `@Component`：**把对象交给容器造**（IoC）。
- `@Autowired` / `@Resource`：**告诉容器「我需要什么」，让它递过来**（DI）。

### 实际收益推演

明天要把数据源从 `user.txt` 换成 MySQL，只需要：

```java
@Repository
@Primary                    // 让 Spring 优先用这个实现
public class UserDaoImplMysql implements UserDao {
    @Override
    public List<String> findAll() { /* 改成 JDBC 查询 */ }
}
```

**Service、Controller 两层完全不用动**，因为它们的代码里从来没有出现过 `UserDaoImpl` 这个名字。

## 七、四类注解速查

### 交给容器的注解（IoC）

| 注解 | 用在 | 说明 |
|---|---|---|
| `@Component` | 不属于以下三层的类 | 基础注解 |
| `@Controller` | 表现层 | 配 `@ResponseBody` 才返回数据 |
| `@RestController` | 表现层 | = `@Controller` + `@ResponseBody`，**返回对象自动转 JSON** |
| `@Service` | 业务层 | 语义标注 |
| `@Repository` | 数据层 | 语义标注；整合 MyBatis 后用得较少 |

> 这四个功能上等价，**区别只是语义**。换着用程序照样跑，但没人会这么干——注解是给读代码的人看的。

### 注入依赖的注解（DI）

| 注解 | 来源 | 匹配方式 | 备注 |
|---|---|---|---|
| `@Autowired` | Spring | **按类型** | 类型有多个 Bean 时需 `@Qualifier` 或 `@Primary` |
| `@Resource` | JDK（`jakarta.annotation`） | **按名字**（默认取字段名），可用 `name` 指定 | 本项目 Controller 用了 `@Resource(name = "userService")` |

三种注入写法（属性 / 构造器 / setter）的优缺点对比 → 见 `IOC&DI.md`。

> **实践建议**：日常开发用**构造器注入**。理由：字段可声明为 `final`、依赖关系一眼看清、单测时直接 `new` 就能传假对象。属性注入写起来最省事，但隐藏依赖，是 Spring 官方不推荐的首选。

## 八、常见坑（踩过才算学过）

### 1. 前后端字段名不一致 → 页面上某列空白 ⚠️ 本项目现存问题

- `User.java` 里字段是 **`createTime`**
- `user.html` 里写的是 **`{{user.updateTime}}`**
- `UserServiceImpl` 里那个局部变量也叫 `updateTime`

三处名字两套，后果：**JSON 里字段叫 `createTime`，前端取 `user.updateTime` 取不到 → 表格「更新时间」列会渲染成空白。**

**两种改法（二选一，改一处不够，要改同一侧的一组）：**

| 方案 | 需要改 |
|---|---|
| 以实体为准 | `user.html` 的 `user.updateTime` → `user.createTime`；`UserServiceImpl` 里变量名 `updateTime` → `createTime`（可选，只为可读性） |
| 以页面为准 | `User.java` 的 `createTime` → `updateTime`；表头「更新时间」保持不变 |

> 这类 bug 的排查思路值得记住：**浏览器 F12 → Network → 点 `/list` → 看 Response 里的实际字段名**。以「接口真实返回」为准去核对前端取值，而不是盯着 Java 代码猜。

### 2. `NoSuchBeanDefinitionException`（找不到 Bean）

八成是这三种原因：

- 忘记加 `@Repository` / `@Service` / `@Controller` 等注解；
- 类不在启动类所在包的**同级或子包**下（`@SpringBootApplication` 只扫描自己所在包及子包）；
- 手动 `new` 的对象里做注入——不是 Spring 造的，容器管不着它。

### 3. `NoUniqueBeanDefinitionException`（找到多个 Bean）

`UserDao` 有多个实现类时，容器不知道该注入哪个。解法：

```java
@Primary                          // 方案一：指定默认优先
@Qualifier("userDaoImplMysql")    // 方案二：按名字精确指定
@Resource(name = "userDaoImplMysql")  // 方案三：@Resource 天然按名字
```

### 4. 改了文件不生效

`resources` 下的文件（`user.txt`、`user.html`）会被复制到 `target/classes/` 才被读取。改完源码没重新编译，跑的还是旧副本。IDEA 里按 `Ctrl + F9` 重新构建，或直接用 `spring-boot:run`。

### 5. 端口被占 / 启动端口不是 8080

- 检查是否已有实例在跑（一个端口只能被一个进程监听）；
- 排查配置覆盖：`application.properties` → 命令行参数 `--server.port=8081` → 环境变量，**优先级依次升高**。

### 6. 把注解写错位置

`@Service` 贴在接口上没用——**注解只能贴在实现类上**，因为接口不能被实例化。

## 九、本项目的教学遗留痕迹

学习项目里为演示知识点留下的冗余代码，知道它们「为什么在」就行，真实项目要清掉：

| 位置 | 现象 | 说明 |
|---|---|---|
| `UserController` | `@Resource` 属性注入 + `@Autowired` 构造器注入**同时存在**，注入同一个 `userService` | 为了演示三种注入方式，实际是重复注入，无副作用但冗余；正式代码只留一种（推荐构造器） |
| `UserController.java.bak` | 备份文件 | 可删，不影响运行 |
| `UserDao.findAll()` 返回 `List<String>` | 教程为了「数据来自文件」做的简化 | 真实项目 DAO 直接返回 `List<User>`，解析工作由 ORM 框架完成 |
| `UserServiceImpl` 里的 `updateTime` | 与实体字段名不符 | 见第八章第 1 条 |

## 十、自测清单

能全部答上来，这一章就算通关：

1. 三层的名字、包名、注解分别是什么？各自的职责边界在哪？
2. 为什么接口和实现类要分开放（`dao` / `dao.impl`）？
3. `@Autowired` 和 `@Resource` 的区别是什么？
4. 为什么 Service 里写 `private UserDao userDao;` 不写 `new` 也不会报空指针？
5. Spring 启动时，`UserDaoImpl`、`UserServiceImpl`、`UserController` 的创建顺序是怎样的？
6. 数据从文件到页面上的一张表格，中间经历了哪三种数据形态？
7. 如果把数据源换成 MySQL，需要改哪几层？为什么其余层不用改？
8. `@RestController` 相比 `@Controller` 多做了什么？
9. 页面某列显示空白，你的第一步排查动作是什么？（答案：F12 看接口真实返回的字段名）

### 动手练习（建议按顺序做）

1. **改 bug**：按第八章方案修复 `updateTime` / `createTime` 不一致，重启后确认「更新时间」列有值。
2. **加一层逻辑**：在 `UserServiceImpl.findAll()` 里加过滤——只返回年龄 ≥ 20 的用户。体会「业务规则应该写在 Service 而不是 DAO 或 Controller」。
3. **换实现**：新写 `UserDaoImplMysql`（先写个假数据版本也行），用 `@Primary` 让 Spring 改用它，验证 Service 层是否真的一行没改。
4. **删冗余**：把 `UserController` 的重复注入清掉，只保留构造器注入，重启验证 `/list` 仍正常。
